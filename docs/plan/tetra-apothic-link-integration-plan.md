# Tetra Apothic Link：Tetra/Tetrawear × Apotheosis 联动策划

> 状态：兼容底座、默认 Tetra 工具分类、真实攻击上下文与六种特殊能力词缀已进入代码实现，仍待实机平衡与完整客户端回归。  
> 更新日期：2026-08-14。  
> 本文只描述设计和实现边界，不代表当前源码已经完整实现所有内容。

## 1. 项目定位

`Tetra Apothic Link` 是 Forge 1.20.1 独立附属，用于让 Tetra/Tetrawear 模块护甲更可靠地参与 Apotheosis 的装备分类、词缀、重铸、孔位和宝石系统，并处理两套数值系统叠加后的平衡问题。

- Tetra/Tetrawear 继续负责装备结构、模块、材料、完整度、敏捷与精力系统。
- Apotheosis 继续负责战利品稀有度、词缀、重铸、孔位、宝石和拆解。
- 本附属只提供分类桥接、适用规则、数据保存修复和平衡联动。
- 不修改或重分发 Tetra、Tetrawear、Apotheosis。
- 公开 API 优先；只有上游缺少扩展点时才使用最小范围 Mixin。

### 目标版本

- Forge 47.4.16
- Tetra 6.17.0
- Tetrawear 1.0.0
- Apotheosis 7.4.8
- Placebo 8.6.3
- Apothic Attributes 1.3.7
- Tetracelium 1.3.2（可选兼容）
- Create: Enchantment Industry 2.5.0b（可选兼容）

升级任一核心模组后，需要重新审计 Mixin 目标、`LootCategory` 调用链、宝石校验和 Tetrawear 精力结算路径。

## 2. 轻甲与重甲分类

### 2.1 分类原则

- 按单件装备独立分类，允许轻头盔、重胸甲等自由混穿。
- 分类实时读取当前模块和材料，不把轻重类别永久写入物品 NBT。
- 禁止使用已经包含 Apotheosis 词缀、宝石或其他外部加成的最终护甲值作为分类依据。
- 非 Tetrawear 模块护甲继续使用 Apotheosis 原生类别。
- Apotheosis `TYPE_OVERRIDES` 保持最高优先级，整合包作者可以强制覆盖异常物品。

### 2.2 新增类别

注册八个 Apotheosis `LootCategory`：

- `light_helmet`、`heavy_helmet`
- `light_chestplate`、`heavy_chestplate`
- `light_leggings`、`heavy_leggings`
- `light_boots`、`heavy_boots`

每个类别映射到对应原版父类别，例如 `light_helmet` 回退到 `apotheosis:helmet`。

### 2.3 默认重量规则

结构重量：

- 布、皮结构：0
- 锁甲结构：1
- 板甲结构：2
- 重型肩甲、重型腿甲等结构：3

材料修正：

- 轻质材料：-1
- 普通材料：0
- 致密、超重材料：+1

最终总重量 `< 2` 为轻甲，`>= 2` 为重甲。

- 未配置但提供护甲或韧性的承重模块默认按重量 2 处理，避免未知承重模块被误判为轻甲。
- 未知材料默认修正为 0。
- 模块与材料规则应支持按 ID 和标签通过数据包覆盖。

### 2.4 公共接口

计划保留以下公共查询接口：

- `getArmorWeight(ItemStack)`
- `classify(ItemStack)`，返回 `LIGHT`、`HEAVY` 或 `NOT_APPLICABLE`
- `getLootCategory(ItemStack)`
- `explainLootCategory(ItemStack)`，返回规则来源、命中规则和当前模块结构快照
- `GatherArmorWeightEvent`，允许其他 Tetra 附属追加重量、覆盖重量或强制分类
- `/tetraapothic inspect`，显示模块、材料、重量贡献、最终类别、父类别和 Apotheosis NBT 状态

## 3. Apotheosis 兼容底座

### 3.0 Tetra 工具动态分类与远程属性兼容

- Apotheosis 7.4.8 原生只用 `BowItem` 和 `CrossbowItem` 识别弓、弩；Tetra 模块化弓弩继承 `ModularItem`，还会因主手攻击伤害误入 `sword` 类别。
- 工具主类别由 `data/*/tetra_apothic_link/tool_categories/*.json` 决定。规则可以匹配物品 ID/标签，以及当前模块槽位、模块 ID、variant、材料 ID/标签和 Tetra `ItemEffect`。
- 每条规则带 `priority`，按优先级从高到低只选择一个主 `LootCategory`；相同优先级按规则 ID 稳定排序。禁止把候选类别同时应用，避免重铸、词缀池和宝石校验重复执行。
- `all`、`any`、`none` 条件分别表示全部存在、至少存在一项和全部不存在；分类实时读取当前物品结构，不写入永久 NBT。
- 默认数据覆盖 Tetra 6.17.0 原版模块化弓、弩、盾、剑、双头工具和单头工具；Java 类判断仍只作为弓弩数据未绑定或未命中时的安全回退。
- 默认优先级为：远程 `1000` > 盾 `900` > 三叉戟 `800` > 重型武器 `700` > 镐 `600` > 铲 `500` > 剑/矛 `400` > 明确无合适类别 `0`。双头工具同时存在斧/锤与镐时稳定选择重型武器，不因模块枚举顺序变化。
- 默认映射如下：

| Tetra 结构 | Apotheosis 类别 |
|---|---|
| 模块弓、模块弩 | `bow`、`crossbow` |
| 模块盾 | `shield` |
| 原版三叉戟头 | `trident` |
| 重刃、斧、锤、锛 | `heavy_weapon` |
| 镐头、Earthpiercer、Stonecutter | `pickaxe` |
| 铲头 | `shovel` |
| 普通模块剑与矛头 | `sword` |
| 锄、镰、提取器、爪等没有原生神化对应池的双头工具 | `none` |

- `none` 是明确分类，不再让正攻击伤害把锄、镰等工具误判成剑；整合包仍可用更高优先级数据规则将任一模块组合改入自定义类别。
- 分类桥接位于 Apotheosis 原生 `TYPE_OVERRIDES` 检查之后、通用类别遍历之前，因此整合包作者的显式强制分类仍具有最高优先级。
- 未命中数据规则的 Tetra 工具继续走 Apotheosis 原生判定，不创建额外的武器子类别。
- 模块切换会改变分类，所以所有 Tetra 模块物品都绕过 Apotheosis 仅按 `ItemStack` 保存的 Affix/Gem 派生缓存；服务端规则同步到客户端，保证 Tooltip 与实际类别一致。

原版神化属性还存在“分类成功但行为不生效”的独立问题：

- `attributeslib:draw_speed` 原生只允许 `ProjectileWeaponItem` 和 `TridentItem` 进入 `LivingEntityUseItemEvent.Tick` 修正；Tetra 弓弩不是 `ProjectileWeaponItem`，因此原路径确定无效。
- 本附属在 Tetra 自己的 `getDrawDuration` / `getReloadDuration` 结果上应用玩家最终 `draw_speed` 倍率，使拉弓进度、模型进度、松手判定和弩装填音效继续共享 Tetra 原生时长；不再同时放宽 Apothic Attributes 的逐 Tick 修正，避免双重加速。
- `attributeslib:arrow_damage` 与 `attributeslib:arrow_velocity` 不检查弓类，而是在 `AbstractArrow` 加入世界时读取其 owner。Tetra 普通弓箭和弩箭都在 `addFreshEntity` 前把发射玩家设为 owner，因此沿用 Apothic Attributes 原生乘算，不额外重复乘伤。
- 弩发射烟花和其他非 `AbstractArrow` 投射物不吃 `arrow_damage`，与 Apothic Attributes 原生语义一致；若未来要支持，必须另设明确效果，不能伪装成箭矢伤害兼容。

示例：

```json
{
  "replace": false,
  "rules": [
    {
      "id": "greatsword",
      "priority": 100,
      "items": ["tetra:modular_sword"],
      "module_slots": {
        "all": ["sword/blade"],
        "none": ["sword/hilt/light_grip"]
      },
      "modules": {
        "any": ["sword/basic_blade"]
      },
      "variants": {
        "any": ["sword/basic_blade/greatsword"]
      },
      "category": "heavy_weapon"
    }
  ]
}
```

### 3.1 父类别回退

- 词缀和宝石先检查轻甲或重甲精确类别。
- 没有精确内容时，只回退一次到对应原版头、胸、腿、脚类别。
- 禁止同时应用精确类别和父类别效果。
- 八个新类别都必须被 Apotheosis 视为 defensive/armor 类别。
- 随机战利品、重铸、稀有度验证、词缀命令、已有装备读取、孔位、宝石镶嵌和宝石加成都要使用同一套回退规则。

### 3.2 适用与休眠

- 轻甲、重甲词缀和宝石的 allow/deny 规则由数据包定义。
- 中性生存、环境和功能内容继续通过父类别继承。
- 已有装备在模块更换后变成不适用类别时，不删除词缀或宝石 NBT。
- 不适用内容进入休眠，Tooltip 显示原因；装备切回适用类别后自动恢复。
- 孔位数量完全遵循 Apotheosis 原生规则，不与 Tetra 魔力容量或轻重分类绑定。

第一阶段以完整兼容为目标，不主动禁止原版词缀或宝石；轻重甲差异化规则在第二阶段数据包中启用。

### 3.3 原版宝石增量补丁

- Apotheosis 的 `data/apotheosis/gems` 注册表按资源 ID 整体替换 JSON，本身不支持跨数据包合并 `bonuses`；本附属不再覆盖原版宝石完整定义。
- 数据包可在 `data/<namespace>/tetra_apothic_link/gem_bonus_patches/*.json` 中指定目标 Gem ID，并只提供需要追加的 `bonuses`。
- 每次数据包重载都以 Apotheosis 刚加载的原始 bonus 列表为基线重新组合；删除或修改补丁后不会留下旧效果，也不会因重复重载叠加。
- 补丁监听器只保存原始 bonus JSON，实际解码延迟到 Apotheosis Gem 注册表完成重载后，避免提前访问尚未绑定的 `LootRarity` holder。
- 增量 bonus 不得占用目标 Gem 已有或另一条增量 bonus 已占用的 `LootCategory`；发生冲突时整条 bonus 被拒绝并写入日志，防止 Apotheosis 构造重复类别映射时崩溃。
- 组合后的完整 Gem 仍由 Placebo 原生同步给客户端；客户端接收远程服务器的 staged Gem 注册表时不得再次应用本地补丁，因此服务端数据包保持权威，无需客户端复制同一份完整原版 JSON。

示例：

```json
{
  "target": "apotheosis:core/guardian",
  "bonuses": [
    {
      "type": "apotheosis:attribute",
      "gem_class": {
        "key": "tal_light_guardian",
        "types": ["light_chestplate", "light_leggings"]
      },
      "attribute": "tetrawear:energy_defence_cost",
      "operation": "MULTIPLY_TOTAL",
      "values": {
        "common": -0.03,
        "uncommon": -0.05,
        "rare": -0.07,
        "epic": -0.09,
        "mythic": -0.12,
        "ancient": -0.15
      }
    }
  ]
}
```

### 3.4 装备转换与 Tetracelium

本附属注册较晚执行的 Tetra replacement 规范化处理：

- 正确复制 `affix_data`。
- 只有来源实际存在 `apoth_boss` 时才复制。
- 如果目标根级 `apoth_boss` 错误保存了 `affix_data` 副本，则清除错误字段。
- 拒绝复制损坏、类型不符或无法解析的 Apotheosis NBT。

Tetracelium 1.3.2 的 `AffixReplacementHook` 会正确复制 `affix_data`，但错误地再次读取 `affix_data` 并写入 `apoth_boss`。本附属在安装 Tetracelium 时负责规范化其结果；未安装时也能独立保存 Apotheosis 数据。

## 4. 精力主动攻击与高护甲平衡

### 4.1 主动攻击的真实结算路径

Tetrawear 的 `tetrawear:energy_attack_damage` 是“主动攻击伤害”，不是独立的能力伤害类型。

1. Tetrawear 在服务端 `AttackEntityEvent` 中读取主动攻击修饰符。
2. 修饰符被临时转移到 `minecraft:generic.attack_damage`。
3. 玩家执行正常近战攻击。
4. 同 tick 移除临时修饰符。

因此主动攻击增量会参与：

- Apothic Attributes 暴击。
- 生命窃取。
- 护甲穿透和护甲撕裂。
- 普通攻击伤害属性与武器伤害词缀。
- Tetrawear Charge 等下一击增伤。

以下独立额外伤害不属于主动攻击增量：

- 当前生命值百分比伤害。
- 火焰、寒冷等额外伤害包。
- 雷击、横扫和其他独立 `DamageSource`。
- Apotheosis 词缀单独生成的伤害。

### 4.1.1 真实 Tetra 攻击上下文

本附属在 `Player.attack` 入口创建短生命周期、线程局部且支持嵌套的攻击上下文，并只把该方法内第一次调用原目标 `Entity.hurt(playerAttack, amount)` 的伤害包认定为 `BASE_ATTACK`。

- `AttackEntityEvent` 阶段提前制造的伤害、基础伤害事件内递归调用的 `hurt`、基础伤害后的横扫/连锁伤害，以及递归 `Player.attack` 均判为 `GENERATED_DAMAGE`。
- 上下文保存攻击者、原目标、攻击开始时的主手 Tetra 物品快照、嵌套深度和当前阶段；普通非 Tetra 攻击返回 `NOT_TETRA_ATTACK`。
- 基础伤害完整保留一次 Apothic Attributes 暴击、吸血、过量治疗、当前生命值伤害、火焰/寒冷附伤，以及 Apotheosis 装备和宝石的 `doPostAttack`。
- 派生伤害不再次触发上述进攻属性；递归 `Player.attack` 还会跳过神化装备/宝石的攻击后能力、Tetra 核心 `AttackEntityEvent` 入口和 Tetrawear 主动攻击精力转移，并禁止再次产生原版或神化暴击。
- 受击方的护甲、减伤、抗性、护甲词缀、宝石 `onHurt` 和其他防御处理不被整体取消，因此二次伤害仍按其自身 `DamageSource` 正常受防御系统处理。
- 公开查询入口为 `TetraAttackContext.current()`、`damageKind(...)` 和 `isGeneratedDamage(...)`；第三方附属主动生成延迟伤害时应使用 `runGeneratedDamage(...)` / `callGeneratedDamage(...)` 包裹实际结算。
- 仅靠当前线程无法自动识别若干 tick 后才执行、且没有包裹或专用伤害标记的第三方延迟伤害；这类兼容必须由来源附属接入公共上下文，不能按“玩家当前手持 Tetra”猜测。

Apotheosis 的 `AffixType.ABILITY` 只是特殊能力词缀的生成分类，Festive、Cleaving、Potion 等都可以属于该类型；它不是统一的“能力伤害”通道。Apothic Attributes 1.3.7 也没有 `ability_damage` 属性。

如果未来需要兼容某个物品右键技能或其他模组能力伤害，必须按其实际 `DamageSource` 和事件链单独审计，不能假设它自动继承主动攻击兼容。

### 4.2 最终护甲抑制

高额 Apotheosis 护甲会放大 Tetrawear“低基础护甲换高主动伤害”的收益，因此只对 Tetrawear 主动攻击增量应用最终护甲抑制：

`倍率 = max(最低倍率, 1 / (1 + max(0, 最终护甲 - 软上限) / 衰减跨度))`

默认值：

- 软上限：24 护甲
- 衰减跨度：40
- 最低倍率：25%

默认结果：

- 24 护甲及以下：100%
- 44 护甲：约 66.7%
- 64 护甲：50%
- 94 护甲：约 36.4%
- 极高护甲：最低保留 25%

规则：

- 服务端读取攻击者当前最终 `minecraft:generic.armor`，覆盖词缀、宝石和其他模组的堆甲来源。
- 只缩放本次攻击中由 `energy_attack_damage` 产生的增量。
- 不缩放武器基础伤害、普通 Apotheosis 伤害词缀和独立额外伤害包。
- 启用开关、软上限、衰减跨度和最低倍率进入服务端配置，并同步给客户端 Tooltip。

## 5. 装备能力词缀效果池

本附属将 Apotheosis 内容明确分为两层：

- 普通 `STAT`/Attribute Affix 只提供基础、常驻、可直接理解的数值加减，例如敏捷、护甲、韧性、击退抗性、精力回复倍率及攻击/防御精力消耗。
- 需要事件监听、条件窗口、共享冷却、次数、缓冲池或状态转换的特殊效果实现为装备自身的黄色 `ABILITY` Affix，不再放在宝石上，也不实现为玩家 Attribute。
- 普通词条允许四件护甲按 Apotheosis 原生方式叠加，但需要缩小同稀有度随机波动，避免装备差异主要来自一次随机浮动。
- 每个特殊效果 Affix 限制到一个明确的精确轻重甲类别，例如借隙只用于轻型靴子、震阵只用于重型胸甲，从生成层避免四槽自然堆叠。
- 特殊效果进入 Apotheosis 黄色能力词条区，参与随机掉落、重铸、词缀命令、稀有度验证及每件物品的能力词缀数量预算。
- 原版宝石只保留已有的基础数值联动或 Apotheosis 原生行为，不再作为六个事件机制的载体。

本节定义装备能力词缀可承载的特殊效果。所有效果仍必须安全处理物品复制、换装、主副手变化和其他模组槽位，不能假定一个玩家永远只有一个来源。

### 5.1 统一叠加规则

- 每个玩家、每种效果只有一个运行实例。
- 多个装备来源先汇总成最终效果等级，再进行一次触发判定。
- 禁止每件装备分别投掷触发概率或分别创建冷却。
- 所有来源共享冷却、触发窗口、缓冲池、次数和临时状态。
- 二值机制默认采用最高等级生效；数值机制才允许累加，并设置硬上限。
- 主手提供同名效果时进入同一个汇总池，不能额外触发一次。
- 同一个伤害、闪避或精力事件最多触发同名效果一次。
- 如果必须使用概率，只进行一次汇总后的最终判定，且默认不得因多来源达到 100%。

### 5.2 能力词缀与槽位分配

六个事件机制全部注册为本附属的独立 `ABILITY` Affix：

| 护甲路线 | 槽位 | Affix ID | 特殊效果 | 作用定位 |
|---|---|---|---|---|
| 轻甲 | 胸甲 | `tetra_apothic_link:ability/light/breathing` | 调息 | 脱离交战后逐步提高自然回复。 |
| 轻甲 | 护腿 | `tetra_apothic_link:ability/light/resurgence` | 复起 | 自然解除耗尽后强化一次手动闪避。 |
| 轻甲 | 靴子 | `tetra_apothic_link:ability/light/opportunity` | 借隙 | 手动闪身后的首次成功回避返还部分实际费用并反制。 |
| 重甲 | 护腿 | `tetra_apothic_link:ability/heavy/chain_pressure` | 连锁承压 | 针对多段攻击降低窗口内后续防御费用。 |
| 重甲 | 胸甲 | `tetra_apothic_link:ability/heavy/buffer` | 缓冲层 | 将一次重击的部分最终伤害延后结算。 |
| 重甲 | 胸甲 | `tetra_apothic_link:ability/heavy/shockwave` | 震阵 | 承受一次高防御负荷后进行无伤害范围反制。 |

这样分配的原因：

- 六种效果都由 Affix ID、当前精确轻重类别、实际装备槽位和稀有度数据共同决定，运行时不读取宝石 ID。
- 借隙仍只接受手动 Tetrawear 闪身后的真实回避窗口，并只返还该次闪身的部分实际费用；逸流宝石提供的基础闪避不会自行授予借隙。
- 轻甲三个能力分别占用胸甲、护腿、靴子的黄色能力词缀预算；重型胸甲的缓冲层与震阵同属 `ABILITY`，在正常生成和重铸中形成选择，重型护腿由连锁承压占用能力预算。
- 头盔暂不分配特殊效果，保留给普通数值宝石与未来内容；主手也不承载这六种护甲效果。
- 原版月华、斗争、逸流、战斗、护卫、稳定及其他宝石的轻重甲差异化 JSON 只负责基础数值，不承担这些事件效果。

### 5.3 调息

定位：需要主动创造喘息时间的加速恢复，而不是普通的少量回复属性。

> 精力开始自然恢复后，如果玩家没有消耗精力、攻击或疾跑，回复倍率逐步提高；进行上述动作后立即重置。

当前原型基线由 `tetra_apothic_link/special_effects` 数据规则定义：

- 普通至远古的起始倍率约为 105%–120%。
- 持续调息约 1.5 秒后达到 115%–150%。
- 持续调息约 3 秒后稳定在 125%–200%。
- 不缩短原始恢复等待，不改变耗尽解除阈值。
- 耗尽状态继续保留 Tetrawear 原生回复惩罚；调息后的耗尽回复速度最多相当于正常回复的 75%。
- 消耗精力、近战/投射物攻击、疾跑、精力回满或恢复过程被打断时，调息进度立即重置。

与普通“单件约 20% 回复速度”属性相比，调息依靠停手窗口获得明显收益，但无法在持续进攻中常驻。

当前载体为轻型胸甲能力词缀 `tetra_apothic_link:ability/light/breathing`；月华宝石的精确类别变体只保留其基础数值联动，不再授予调息。

### 5.4 复起

定位：保留“绝处回气”的主题，但不直接修改精力循环。

> 玩家从耗尽状态自然恢复后获得复起窗口；窗口内下一次手动 Tetrawear 闪避进入持续数秒的脱困冲刺，但仍正常消耗精力，也不提供无敌。

规则：

- 只在 `PlayerEnergy.exhausted` 自然从 `true` 变为 `false` 时触发。
- 不返还精力、不缩短恢复等待、不提高回复量、不降低动作费用。
- 窗口约 8 秒，只能强化一次手动闪避。
- 触发后约 2–3.5 秒内持续解除缓慢与挖掘疲劳，并按词缀稀有度提供约 20%–45% 移速；窗口内新施加的这两类限制也会被清除，但不清除高价值负面效果。
- 不提供穿模、免伤或额外 Evade 次数，避免服务端位移校验与碰撞状态残留。

该效果奖励玩家完整经历耗尽—恢复循环，而不是跳过循环。

当前载体为轻型护腿能力词缀 `tetra_apothic_link:ability/light/resurgence`；斗争宝石不再授予复起。

### 5.5 借隙

定位：奖励真正避开攻击，以有限返费和目标限定的短暂反击机会补足单纯控制的回报，同时不提高基础闪避率。

> Tetrawear 手动闪身后的短暂窗口内，如果一次攻击确实被 Tetrawear Evade 或 Apothic Attributes 闪避取消，则触发借隙。

建议行为：

- 判定窗口基础为 2 秒，从实际完成的 Tetrawear 手动闪身开始计算；如果该次闪身获得的 Tetrawear Evade 实际持续时间更长，则跟随该效果的剩余持续时间。
- Tetrawear Evade 的等级代表持续时间内可回避的次数；借隙只消费该次手动闪身对应的一个窗口，因此首次成功回避会触发，剩余回避次数继续免伤但不会再次返费、失衡或刷新反击。
- 近战攻击：令普通攻击者短暂失衡并打断当前攻击动作。
- 投射物：只将其视为成功避开的攻击并识别原发射者；不再改写所有者、速度或飞行方向。
- Boss 只受到削弱版失衡，不允许长时间控制。
- 成功借隙返还该次手动闪身实际精力费用的 25%–60%；实际费用通过扣费前后差值记录，因此自动适配费用属性和服务端配置。
- 返费不按最大精力计算、不超过该次实际费用、不解除耗尽、不缩短恢复等待；没有真实避开攻击时没有返还。
- 成功借隙后标记原攻击者约 2–3.5 秒；玩家下一次对该目标造成的最终伤害提高至 115%–150%，随后立即消耗标记。
- 反击增伤不作用于其他目标，不提高闪避概率，也不增加免伤次数。
- 使用 2 秒的全身共享冷却，防止多段攻击反复返费或控制。

普通 Apothic Attributes 随机闪避只有发生在手动 Tetrawear 闪身窗口内时才能触发借隙，避免高闪避率被转化为常驻回能或反制。旧的“每件装备独立提供闪避返能”方案仍然撤回；这里使用最高稀有度单一来源、一次手动闪身至多触发一次、真实事件门槛和玩家级共享冷却，不允许四槽、主手或多次 Evade 叠加返还比例。

当前载体为轻型靴子能力词缀 `tetra_apothic_link:ability/light/opportunity`。

### 5.6 连锁承压

定位：针对多段攻击的非线性防御机制，用来替代与现有 `energy_defence_cost` 重复的普通费用减免。

> 主动防御第一次承受攻击时正常支付精力与伤害；随后短暂窗口内，连续攻击的防御精力消耗和最终伤害同时降低，但窗口不会被后续攻击刷新。

建议基线：

- 首次主动防御正常支付精力。
- 按稀有度开启约 30–50 tick 的承压窗口。
- 窗口内后续攻击的防御精力消耗降至正常值的 50%–25%，最终伤害降至 90%–75%。
- 后续攻击不能延长窗口。
- 当前采用约 5 秒全身共享冷却。
- 每个伤害事件只结算一次，避免多件装备分别减费。

首击通过同一 `DamageSource` 实例与游戏刻精确排除，不能提前享受连锁减伤。该效果对怪群、弹幕和多段攻击很强，但对单次重击不减费也不减伤，因此不会取代现有防御费用属性或缓冲层。

当前载体为重型护腿能力词缀 `tetra_apothic_link:ability/heavy/chain_pressure`；战斗宝石不再授予连锁承压。

### 5.7 缓冲层

定位：将重击爆发转化为可处理的持续压力，不直接堆护甲、抗性或生命值。

> 主动防御成功时，将本次最终伤害的一部分转化为缓冲伤害，在之后数秒内逐渐结算。

建议基线：

- 只有本次伤害实际消耗了防御精力时才生成缓冲层。
- 延后约 30% 的最终伤害，分 4 秒结算。
- 缓冲池最多储存玩家最大生命值的约 25%。
- 缓冲伤害使用无攻击实体的专用 `tetra_apothic_link:buffered_damage` 伤害类型，绕过护甲、抗性、附魔、盾牌、受击冷却和冲击，并跳过 Apotheosis 护甲词缀/宝石的 `onHurt` 链、Apothic Attributes 闪避和 Tetrawear 防御精力，不触发生命窃取或荆棘；结算时还要保护玩家已有吸收生命与受击状态，确保已记录的最终生命伤害不会被二次减免，也不会干扰正常攻击的无敌帧。
- 默认不减少总伤害，只平滑爆发；是否允许少量压力自然消散留待实机测试。
- 玩家耗尽时不能继续生成新的缓冲层，已有缓冲仍正常结算。

实现时必须使用专用伤害标记和递归保护，避免缓冲伤害再次生成缓冲层或触发 Apotheosis 伤害链。

当前载体为重型胸甲能力词缀 `tetra_apothic_link:ability/heavy/buffer`，与同为 `ABILITY` 的震阵自然竞争黄色能力词缀预算。

### 5.8 震阵

定位：主动防御承受大伤害后的无伤害范围反制。

> 主动防御成功，且本次攻击达到高防御负荷阈值时，释放一次震阵。

当前原型基线：

- 推开附近普通敌人。
- 使普通敌人短暂减速，并停止其正在使用物品和当前寻路动作。
- 不造成伤害，避免暴击、生命窃取、掉落和连锁攻击。
- Boss 不被推开，只受到短暂、削弱后的减速。
- 防御负荷按 Tetrawear 扣费前的基础公式 `clamp(伤害 × costFactor, minCost, maxCost)` 计算；普通至远古阈值为 0.60–0.35，半径为 3–5 格。
- 仍要求本次主动防御确实扣除了大于 0 的精力；费用减免只降低实际支出，不再反向提高震阵触发难度。
- 使用 8 秒全身共享冷却，按玩家持久数据保存绝对就绪时间，换装、死亡或换维度不能刷新。
- 多个来源只采用最高稀有度的一个实例，不会同时释放多次震阵。

当前载体为重型胸甲能力词缀 `tetra_apothic_link:ability/heavy/shockwave`；Boss 判定覆盖 Forge Boss 标签、Apotheosis Boss/Miniboss 标记与 Fallen universal Boss 标记。

## 6. Tetra 成长与模块效能联动

### 6.1 设计边界

Apotheosis 词缀、宝石和重铸结果属于可随时增加、移除或替换的临时装备层。它们适合改变当前表现和未来成长速度，但不应成为维持 Tetra 装备合法性的结构预算。

- 可以改变即时属性、事件效果、未来获得的打磨进度和白名单内的材料模块结果。
- 不得依靠可重铸内容维持完整度、魔力容量或其他安装合法性条件。
- 效果移除后，装备必须能够立即恢复到纯 Tetra 原始结果，不能留下非法模块、超容量附魔或永久放大的模块 NBT。
- 所有倍率都以 Tetra 原始计算结果为基准，每次只应用一次；禁止在重铸、登录、换模块或数据包重载时重复乘算。
- 禁止修改全局 `MaterialData`、模块定义或共享的 `UniqueVariantData`，避免一件带词缀的装备污染所有同材料装备。

### 6.2 打磨促进

定位：通过正常使用更快获得 Tetra 打磨进度，不直接赠送打磨等级或改进。

> 当前使用的 Tetra 物品获得打磨进度时，提高本次正向进度获取量。

规则：

- 只放大正常传入 `tickHoningProgression` 的正向进度，不直接写入或重置 `honing_progress`。
- 不改变打磨上限、完整度消耗、模块结构、维修成本或已经可用的 `honing_available`。
- 效果失去或休眠后，已有进度保持不变，未来进度恢复原速。
- 不允许负倍率，不允许进度倒退，也不能通过反复换装重新初始化进度。
- 多个玩家级来源先汇总一次，建议硬上限为额外 `+100%`，即最高二倍打磨速度。
- 主手来源与护甲来源进入同一个倍率池；每次实际进度事件只乘一次，禁止五个槽位分别处理同一事件。
- 如果最终载体采用“仅物品自身生效”的设计，则主手上的效果只加速该物品自身，护甲上的同名效果不应跨槽放大主手。载体确定时只能选择一种作用域，不能同时应用玩家级与物品级版本。

打磨促进是本节优先实现的正式内容，因为重铸移除它只会影响未来成长速度，不会改变装备当前合法性。

### 6.3 精工

定位：使一件模块装备更充分地发挥自身材料特性，但不修改材料本身，也不提供结构资源。

> 提高承载该效果的 Tetra 物品中，由材料 `primary`、`secondary`、`tertiary` 三值生成的白名单正向结果。

默认采用物品局部作用域：

- 效果只增强承载它的那一件模块装备。
- 四件护甲和主手可以分别拥有精工，但每件物品只读取自己的精工强度。
- 护甲上的精工不会共同放大主手武器，主手精工也不会增强护甲。
- 同一物品存在多个精工来源时先汇总，再应用一次物品级硬上限。

允许缩放的结果：

- 明确列入数据白名单的连续数值型 Tetra Attribute。
- 明确列入数据白名单、确实以材料三值为输入的连续数值型 `ItemEffect`。
- 第三方模块只有主动声明支持或被整合包数据规则加入白名单后才能参与。

明确排除：

- 完整度与完整度消耗。
- 魔力容量与附魔占用。
- 工具等级、挖掘等级和任何门槛型数值。
- 耐久度、维修消耗和打磨上限。
- `toolEfficiency`；如果以后需要提高工具效率，应作为独立效果设计，不混入材料三值精工。
- 负值、代价、布尔开关、触发次数、整数等级型效果和未声明支持的第三方效果。

实现约束：

- 以当前物品未经本附属修改的 Tetra 原始组合结果为基准，生成只读的运行时覆盖层，禁止把放大结果写回模块 NBT。
- 不修改注册表中的材料或模块定义，不复用已经被其他物品修改过的共享对象。
- 重铸、模块替换、材料替换、词缀休眠、登录和数据包重载后必须刷新相关属性、效果、工具与 Tooltip 缓存。
- 缓存键必须包含该物品当前的精工效果摘要，或在变化时显式失效，不能只依赖 Tetra 原有模块 NBT 缓存键。
- 实际属性、战斗效果、Holosphere/工作台预览和 Tooltip 必须使用一致的倍率与舍入规则。
- Tooltip 应显示“原始 Tetra 值 → 精工后值”，并标明哪些结果因不在白名单而未受影响。

数值建议：

- 初始测试倍率为 `+5%` 至 `+10%`。
- 单件物品建议硬上限不超过 `+15%`。
- `+25%` 只考虑用于单个明确指定的模块或单一结果域，不能默认放大整件物品的全部三值结果。

精工列为实验内容。只有在完成缓存、预览、模块切换和第三方模块白名单回归后，才进入默认数据包。

### 6.4 禁止由可重铸内容提供魔力容量

魔力容量是 Tetra 附魔合法性和失稳计算的预算，不是普通战斗属性。

- 如果玩家依靠词缀临时获得容量并安装高占用附魔，之后重铸移除容量，已有附魔不会自动退回或移除。
- 后续附魔、工作台条件、容量匹配与失稳计算会看到负可用容量，造成前后不一致。
- 这还会形成“先洗容量、安装附魔、再洗掉容量”的绕过路径。

因此词缀、宝石、休眠效果和其他可重铸内容均不得直接增加 Tetra 魔力容量。若未来确有需要，只能设计为不可随意移除的永久 Tetra 改进，并在移除前验证当前容量占用；该方向不属于当前 Apotheosis 联动范围。

### 6.5 禁止由可重铸内容提供完整度

完整度是 Tetra 安装模块时使用的结构合法性预算。

- Tetra 工作台会在安装或修改模块时检查 `integrity >= integrityUsage`。
- Apotheosis 重铸不经过该检查。
- 如果重铸移除了临时完整度，现有模块不会自动卸下，装备会直接进入完整度不足的非法结构。
- 非法装备可能继续存在和使用，但后续工作台操作会被完整度检查阻止。

因此任何可重铸、可休眠、可卸除的本附属内容都不得提供完整度，也不得降低当前模块的完整度消耗。完整度只能继续来自 Tetra 自身材料、模块、改进和受其工作台合法性检查约束的永久来源。

### 6.6 相关兼容保护

- 神化重铸必须保留合法的 `honing_progress`、`honing_available`、模块改进与其他 Tetra 自有 NBT；不得把打磨状态当作可重建的派生数据清除。
- 模块或材料变化后，立即重算轻重类别、精工白名单结果、词缀/宝石休眠状态和联动缓存。
- 神化词缀、宝石或稀有度变化后，也必须清理本附属使用的 Tetra 属性、效果与 Tooltip 派生缓存。
- Apotheosis 拆解会永久销毁装备，而模块装备可能包含远高于普通词缀装备的材料与打磨投入。默认应阻止模块装备进入拆解，或至少要求数据/服务端配置显式允许；不能无提示地按普通词缀装备处理。
- 如果未来允许拆解模块装备，必须明确其只返还 Apotheosis 稀有度材料，还是同时处理 Tetra 模块投入；在该规则确定前不开放默认拆解。
- 第 4.1 节已经确认 Tetrawear 主动攻击增量会进入普通近战伤害链。其他右键技能、独立 `DamageSource` 或第三方能力仍需逐条审计，不能仅凭“能力攻击”名称推定兼容。

## 7. 已撤回的效果

### 7.1 闪避返能

旧方案撤回原因：普通 Attribute 会沿头、胸、腿、脚和主手直接叠加。Apotheosis 宝石的 `unique: true` 只限制同一件物品不能重复镶嵌，不限制全身唯一，因此多个来源很容易达到或超过 100% 返能。

旧的常驻 Attribute 和每件装备独立返能仍不列入推荐效果池。借隙后来采用的是另一种事件型返费：只取全身最高稀有度来源，要求手动闪身窗口内真实避开攻击，按该次实际扣费返还 25%–60%，并使用全身共享冷却；它不按槽位或 Evade 次数累加，也不能让闪身免费或产生正收益。

### 7.2 守势韧性

旧原型的实际行为是：防御精力被扣除后给予抗性提升 I，持续时间由自定义 Attribute 决定。它不是原版护甲韧性，多来源叠加后还可能形成常驻抗性，因此完全撤回。

### 7.3 固守

普通防御精力消耗降低与 Tetrawear 自带的 `tetrawear:energy_defence_cost` 重复；Tetrawear 原生锻造已经可以把该属性提高到较高水平。特殊效果改用“连锁承压”这种只针对多段攻击的非线性机制。

### 7.4 稳架

普通击退降低与 Tetrawear `unyielding` 重复；原生模块可以直接提供 1.0 击退抗性。提高数值也无法形成新的玩法，因此撤回。

### 7.5 掠影收割

闪避后击杀触发额外掉落与精力、轻重甲和现有战斗循环联系不足，并容易与 Apotheosis Festive 等掉落能力相乘，因此撤回。

## 9. 效果实现公共要求

特殊效果由装备黄色 `ABILITY` Affix 提供，但事件实现仍不应在各事件类中写死某一个具体 Affix ID，而应先通过统一效果聚合层和数据 carrier 规则解析：

- 从四个护甲槽、主手和未来允许的其他槽位收集效果来源。
- 按效果 ID 汇总等级、强度和来源信息。
- 生成玩家级共享运行状态，而不是物品级独立状态。
- 冷却和缓冲池保存在服务端玩家数据中，并同步必要的客户端 Tooltip/状态图标。
- 装备切换后立即重算强度，但已有冷却不能通过换装清除。
- 效果来源失效或休眠时停止贡献强度，不删除物品 NBT。
- 数据包负责数值、适用类别、互斥组和上限；Java 代码只负责事件机制和安全边界。

### 12.2 附魔结构资源

Tetra 6.17.0 已在 `EnchantmentHelper.setEnchantments` 后执行 `TetraEnchantmentHelper.mapEnchantments` 和 `assemble`，并按附魔等级扣除对应主模块的魔力容量。CEI 2.5.0b 的烈焰附魔器、附魔书打印和机械砂轮也统一走该入口，因此附魔增删会自动刷新 Tetra 的原生容量占用。

但 CEI 原生不会调用 Tetra 工作台的 `CraftingEffectRegistry`，所以容量变为负数并不等于立即执行去稳化。本附属在 CEI 生成附魔结果时比较操作前后每个主模块的去稳化概率，只记录“本次操作新增的超载概率”，并将待结算数据临时保存在结果物品中；只有机器真正完成加工并提交结果时才进行结算，取消或中断加工不会触发。

每台新旧烈焰附魔器都在自身 BlockEntity NBT 的 `tetra_apothic_link:overload_mode` 中保存一个明确模式。新放置机器和没有该字段的旧机器会读取服务端 `create_enchantment_industry.default_overload_mode`，随即将结果固化到机器 NBT；以后修改服务器默认值只影响尚未初始化的机器，不会暗中改变既有机器。

玩家可选策略只有三种：

- `LIMIT`：默认策略。保留原装备附魔与本次新增诅咒，只逐级降低本次新增的普通附魔，直到所有 Tetra 主模块的剩余魔力容量均不小于零。
- `DESTABILIZE`：保留完整附魔结果，完成加工时按 Tetra 6.17.0 的概率与循环规则结算本次新增的超载。
- `REJECT`：结果会新增超载时返回原物品，使该次加工不能开始。

`create_enchantment_industry.overload_handling_enabled=false` 是服务器级兼容开关。关闭后所有 CEI 附魔器都保留原生结果，即使 Tetra 魔力容量变为负数也不执行限制、拒绝或去稳化；该状态不是玩家模式，不能通过附魔调谐器选中。`allowed_overload_modes` 仅接受 `LIMIT`、`DESTABILIZE` 和 `REJECT`，用于限制玩家能在机器上选择的模式。

旧版本保存的 `INHERIT`、`OFF`、空值或无效模式会在读取时迁移为当前服务器默认模式并写回明确值。其中旧 `OFF` 不再保留为单机豁免，避免某台机器成为无代价超载入口。

`LIMIT` 不手算附魔容量。每个候选结果都从 CEI 完整结果复制，并真实调用 `EnchantmentHelper.setEnchantments`，由 Tetra 的 `mapEnchantments` 与 `assemble` 将附魔重新映射到各个主模块，然后重新读取每个主模块的剩余容量。具体降级顺序如下：

1. 原装备任一主模块已经超载时，不删除旧附魔，直接拒绝本次操作。
2. 原附魔等级构成不可降低下限；本次新增诅咒也以 CEI 给出的完整等级作为不可降低下限。
3. 如果“原附魔 + 本次新增诅咒”仍然超载，则拒绝本次操作，防止容量模式规避 CEI 诅咒。
4. 从 CEI 完整结果开始，每轮分别尝试把一个可降低的新附魔降低一级，并真实重组装备。
5. 候选依次按最严重模块的标准化缺口、全部模块缺口总和、完全删除的新增附魔种类数、降级分布均匀度和附魔注册 ID 排序；只采用一次最优降级后进入下一轮。
6. 标准化缺口为 `max(0, -remainingCapacity) / max(1, capacityGain)`。这样多个主模块之间可以比较，而不会让容量基数大的模块天然占优。
7. 单次操作最多评估 4096 个候选；超过预算或不存在合法结果时返回原装备。

该算法只修改本次生成结果中的附魔等级，不写入永久的“容量上限附魔”标记。以后通过砂轮移除附魔、工作台换模块或重新重铸时，Tetra 仍按当前真实附魔重新计算容量。CEI 的经验液消耗仍采用机器原生费用规则，不因 `LIMIT` 自动折价；容量限制控制的是结果上限，而不是把高等级机器变成低成本附魔来源。

本附属注册 `tetra_apothic_link:enchantment_tuner`（附魔调谐器）。手持它右击新式或经典烈焰附魔器会在服务器允许的三种模式间切换，潜行右击反向切换；模式修改立即写盘并同步客户端。工程师护目镜始终显示机器的明确模式；全局兼容开关关闭时显示“全局关闭”，调谐器只提示服务器已关闭联动而不修改机器的底层模式。加工结果在 `getResult` 阶段生成并锁入 CEI 的 `ActiveEnchanting`，所以加工途中切换只影响下一件物品，不会改变正在加工的物品。

`DESTABILIZE` 复用 Tetra 数据包中的 `tetra:destabilization/` 子效果池，包括去稳化改进、爆炸、药水云、生成生物和奥术火焰等结果；其中按资源 ID 排除 `tetra:destabilization/lightning_strike`，避免同时保留两种功能重叠的雷击。抽取前仍使用当前装备、主模块槽位、机器位置和服务端世界检查每条子效果的 `requirement`，不会绕过整合包追加的数据条件。自动化机器没有可归属的真实玩家，因此不伪造工作台材料、图纸或玩家成就上下文。`destabilization_scale` 默认 `1.0`，用于整合包调整新增超载概率。

每次新增超载成功触发去稳化时，会同时执行两部分结果：先从排除了原版雷击的 Tetra 子效果池随机抽取一项，再固定执行一次 CEI 召唤雷。两者不是互斥抽取，因此雷击不会挤占诅咒、爆炸、药水云或其他 Tetra 去稳化结果。CEI 召唤雷调用其自身的 `BlazeLightningHelper`，遵循避雷针寻址并保留对经验块充能的特殊标记。`summoned_lightning_enabled` 默认开启；关闭后仍会执行 Tetra 子效果，但不再召唤雷。

本附属不令附魔额外消耗完整度：完整度负责模块结构合法性，魔力容量负责附魔预算；重复计费会使机器加工后的既有装备在没有工作台预检的情况下突然进入完整度不足状态。

### 12.3 验收

- 无 CEI 环境完成客户端启动，确认不出现可选类链接错误。
- 有 CEI 环境用纸和 250 mB 墨水复制多图纸 Tetra 卷轴，比较完整 NBT。
- 分别通过新旧烈焰附魔器增加附魔，验证 `LIMIT`、`REJECT`、`DESTABILIZE` 三种机器模式；取消加工不得结算，完成加工必须清除临时待结算 NBT。
- 验证新机器、无模式字段的旧机器以及旧 `INHERIT`/`OFF` NBT 均固化为当前服务器默认模式；服务器随后修改默认值不得改变已初始化机器。
- 关闭 `overload_handling_enabled` 后验证所有机器均保留 CEI 原生结果、护目镜显示“全局关闭”、调谐器不能切换模式；重新开启后恢复各机器之前保存的明确模式。
- `LIMIT` 覆盖原装备已超载、本次新增诅咒、多个主模块重映射、普通附魔降一级、普通附魔完全移除、无合法候选与 4096 次评估上限；确认旧附魔和新增诅咒从不被降低。
- 用附魔调谐器正向、反向切换新旧机器，验证模式经过区块卸载、重登和服务端重启后仍保留，护目镜显示与服务端实际解析模式一致。
- 在加工开始后切换模式，确认已锁定结果不变且新模式只作用于下一件物品。
- 在 0%、50%、100%、200% 和超过 200% 的新增超载概率下固定随机源，确认结算次数与 Tetra 6.17.0 一致；已存在的旧超载不得被重复计入本次增量。
- 确认每次成功去稳化都会同时出现一个非雷击 Tetra 结果与一次 CEI 召唤雷，且不再抽到 `tetra:destabilization/lightning_strike`；关闭 `summoned_lightning_enabled` 后仍保留 Tetra 结果，但不得产生任何雷击。
- 通过机械砂轮移除附魔，确认 `EnchantmentMapping`、模块魔力容量占用和工作台显示同步刷新，且降低超载不会生成去稳化结算。
- CDR 同时安装 CDC 与本附属时确认只有 CDC 的卷轴打印 provider 生效。

### 12.4 维护约束

- `CraftingEffectRegistry.registerEffectType` 不能在本附属构造函数中调用：Tetra 6.17.0 此时可能尚未建立 `CraftingEffectRegistry.instance`，会在启动阶段空指针。自定义去稳化结果类型必须延后到 `FMLCommonSetupEvent.enqueueWork` 注册。
- Tetra 6.17.0 的 `ExplosionOutcome` 同时使用 JSON 的 `type` 作为多态判别字段和 Java 爆炸交互字段，原版 `destabilization/explosion.json` 反序列化后可能得到空交互类型；`ExplosionOutcomeMixin` 仅在该字段为 `null` 时回退为 `ExplosionInteraction.NONE`，保留爆炸伤害与半径但不破坏方块。
- CEI 2.5.0b 的 Mixin 目标固定为新旧 `EnchanterBehaviour#getResult(ItemStack)` 与两种 `BlazeEnchanterBlockEntity#tick()` 的成功完成分支；升级 CEI 后必须重新核对方法描述符、`heldItem` 写入顺序以及 `finishProcessing()` 调用点。
- 新旧 Behaviour 均通过私有 `enchanter` 字段定位所属机器，机器 Mixin 则注入 `write/read/addToGoggleTooltip` 并实现本附属模式接口；升级 CEI 后还必须复核该字段名、两种 BlockEntity 的 NBT 方法以及护目镜入口。
- `overload_handling_enabled`、`default_overload_mode` 与 `allowed_overload_modes` 必须进入 `SyncedSettings`/`RuleSyncPacket`，不能让远程客户端直接读取本地 SERVER config，否则护目镜的全局状态和调谐器可选模式可能与服务器实际规则不一致。
- 召唤雷通过反射调用 `BlazeLightningHelper#getStrikePos` 与 `strikeLightning`，保持 CEI 为可选依赖；反射失败只记录一次警告并跳过该次结果，不能令主附属在无 CEI 环境硬链接失败。
